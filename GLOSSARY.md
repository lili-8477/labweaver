# Glossary

Memory terms, as in LabWeaver v2 (labweaver `GLOSSARY.md`), with v1's paths.

**Memory contract**: the table of memory-api operations in `hub/indexer/src/memory-contract.ts`. For each operation it gives the HTTP route, the identity field (`username` or `actor`), the caller's input schema (zod) and the result type. The API validates with these schemas, and the repo returns these types. The adapter forwards the UI's `memory_*` RPCs through it, filling in the identity with its own user. mcp-memory derives its tool schemas from it, and the frontend imports its types. A new operation is one contract entry plus one route handler.

**Memory access**: who may see and who may change a memory, decided in `hub/indexer/src/memory-access.ts`. A memory is visible to a viewer when it is theirs or the org's and its access class (`public` < `internal` < `restricted` < `irb`) is within the viewer's clearance (`MEMORY_CLEARANCE`, default `internal`). Every read path applies this rule: search, get by id, timeline, list, tree, directories, the context graph, the bundle and its lineage links. Deleted, superseded and project filters are each query's own choice, not visibility. Only the owner changes a memory (`withOwnedRow`: row lock, owner check, one transaction).

**Caller check**: each user container sends its service ID (`SERVICE_ID`, which the adapter derives from `ID_HASH` and passes to the agent, its hooks and MCP servers) as a Bearer token on every `/memory/` and `/share/` request. The indexer looks it up in `hub/service-map.conf` and refuses an unknown key (401) or a key whose user is not the one the request names (403) (`hub/indexer/src/caller-check.ts`).

**Memory domain**: whether a memory is `lab` knowledge (samples, experiments, protocols, analysis choices, results, lab decisions) or `technical` know-how (code, packages, environment, tool errors). The writer sets it: `memory_write` requires it, and distill requires it on each experience (claims and the run default to `lab`). `hub/indexer/src/memory-domain.ts` holds the guidance the agent follows (`DOMAIN_HELP`). The chat UI is for life scientists, so the adapter pins its listings (search, list, directories, tree, context graph) to `lab` (`UI_DOMAIN`). The agent reads both.

**Outcome loop**: how memory learns from Auto-mode work. When the agent opens a memory (`memory_get` through mcp-memory), the indexer records a use (`memory_uses`) and a hit. After each review round, Auto mode reads the reviewer's verdict from `progress.md` in code (`adapter/src/auto-mode.ts`): the step became `(reviewed)` (success) or got a `reviewer: <step> rejected` note (failure). It then posts `memory_outcome`, which credits that verdict to every memory used since the previous verdict, or since the turn began. Credit is the same as `memory_feedback`: success and failure counts that rank search, and promotion of proven experiences to the lab. A UI read is not a use.

**Reinforcement**: how memory evolves with use (migration 0018). A memory is reinforced when the agent opens it for its work, when new information is merged into it (`memory_merge`), and when a task that used it succeeds. Each reinforcement sets `reinforced_at` and bumps `reinforce_count`, which gives a small rank boost. Time is not in the ranking: a memory never fades, and nothing retires it. A failure does not reinforce, and its failure count lowers the rank.
